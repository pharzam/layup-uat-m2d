# Glossary

Terms, abbreviations, and short definitions for `tally`, the Go command that
counts the lines, words and characters of text files. This is the shared
vocabulary the rest of the docs assume. It is the target of the
[Glossary](engineering-discipline.md#glossary) rule, which has two parts. First: any
change that adds a term, renames one, or changes a meaning updates this file in the
same change. Second — **No undefined abbreviation**: every abbreviation used in any
conversation, context, prompt, reply, or response must have an entry here, and any
LLM or operator who uses one that is missing adds it in the same turn. General-English
abbreviations (`e.g.`, `i.e.`, `etc.`) are exempt unless they carry a
project-specific meaning.

## Quick reference — the words of tally

The terms a reader meets first. The full entries are in the sections below.

| Term | One-line meaning |
|------|------------------|
| Line | A run of characters that ends with a line feed; the last run counts too when the file has no final line feed. |
| Word | A run of characters that are not white space under the Unicode property `White_Space`. |
| Character | One Unicode code point of a text in UTF-8 — not one byte. |
| Row | One line of the output: the selected counts, then the file name, separated by single spaces. |
| `total` row | The last row when two or more files are named: the sums of the files counted without an error. |
| Package `count` | The Go package that counts a reader; the coverage target applies to it. |
| Peak heap | The largest heap in use during a run, sampled every 10 milliseconds. |

## The format — three columns, plus two rules

Each entry is a row in a table with four cells: the term, its abbreviation (or
`—` when it has none), a description of one or two sentences that states what it
is and why it matters here, and a concrete example that makes it real.

Two rules keep the glossary earning its place:

1. **Collision to watch for.** When a term means something different outside this
   project — in a common library, a neighbouring team, or the wider field — say so
   in the Description, in the form "Collision to watch for: …". A word that quietly
   means two things is worse than an unknown word.
2. **Quick-reference table.** Keep the whole glossary skimmable. The short table
   at the top holds the terms of `tally` with a one-line meaning; the full entries
   stay below.

Slices are ordered by dependency and TDD, the test slice first. Collision to watch for: the "domain" a slice is scoped to is an area of the *work*; it is not the kit's "domain-free", which means the kit names no *product* domain. | A change to product code has a test slice (done first) and an implementation slice, each its own gate-passing step. |

One of the three interface kinds named by the rule that a long operation must show progress ([engineering-discipline.md](engineering-discipline.md#progress-indicators-for-long-running-operations)). | A linter that prints `adr-lint: OK` and exits is a CLI program. |

| HyperText Markup Language | `HTML` | The markup language of web pages. It reaches this kit only as the comment form Markdown borrows, which hides a template line from the rendered page. | The example line in `backlog.md` sits inside an HTML comment, so a reader does not see it. |
| Agent entry point | `—` | A file at the repository root that a coding agent loads when it starts work, so the rules are found rather than looked for. This kit ships two, `AGENTS.md` and a one-line `CLAUDE.md` import of it, described in [`agents/README.md`](agents/README.md) and decided by [ADR-0004](adr/0004-ship-agent-entry-points.md). Collision to watch for: not one of the inert forge files under [`templates/`](templates/) — those are copied into place to change a forge's behaviour, while an entry point is live at the root and only tells a reader where the rules are. | An agent that opens `AGENTS.md` first finds the eight gate steps, a pointer to the thirteen rules, and the document that is authoritative for each. |
| Instruction precedence | `—` | The order in which instructions win when two apply: a higher-priority platform or operator instruction outranks the repository's own agent entry point, which in turn defers to the governance documents it summarises. A nested instruction file may add a local constraint and may never weaken the [quality gate](engineering-discipline.md#working-a-task-under-the-quality-gate). | Where `AGENTS.md` and `issue-workflow.md` disagree about a rule, the rule document wins and the summary is corrected in the same change. |
| Independent review | `—` | A review whose reviewer cannot see what the author saw. Independence — not whether the reviewer is a person or an agent — is what the kit requires, at the four levels set out in [Who may review](engineering-discipline.md#who-may-review): context, method, execution, and model. Collision to watch for: not the forge's "approved" button — a rubber-stamped approval has none of the four levels. | A fresh agent session that sees the issue, the diff, and the source documents, but never the author's reasoning, is context-independent. |
| Review lens | `—` | The one question a review round is asked to answer — correctness, guardrails, clean-and-simple, adversarial bug-hunt, semantic agreement, or one reading. A different lens each round is what makes the [rounds](engineering-discipline.md#reviewing-until-findings-decay) decay rather than repeat. | Two agents given the same lens and the same prompt are one reviewer run twice, not two reviewers. |
| Semantic agreement | `—` | That a changed sentence still means what its source means. It is the residual the kit's deterministic checks explicitly do not cover — they prove coverage and structure, never meaning — so it is closed by a clause-by-clause [review](engineering-discipline.md#reviewing-for-semantic-agreement) recorded on the issue. Collision to watch for: not "the linter passed" — a stub of filler words with the right headings passes every assertion. | A summary that softens a "must" to a "should" keeps full coverage and loses semantic agreement. |
| Decision-driving text | `—` | The text an operator acts on, which must admit [one honest reading, not two](engineering-discipline.md#one-reading-not-two) and be falsifiable ([R13](issue-workflow.md#r13--one-reading-not-two)): the issue statement, the acceptance criteria and Definition of Done, a directive to another operator, a plan step, and a review finding. Collision to watch for: narrower than "documentation" — casual prose, a commit message, or a terminal reply is not decision-driving text, and the one-reading rule does not bind it. | An acceptance criterion a reviewer can read two honest ways is decision-driving text with two readings, so R13 sends it back to be rewritten, not interpreted. |
| Cycle cap | `—` | The maximum number of fix-and-review cycles a task may run after its first frozen head, declared in the plan-review confirmation and defaulting to two. Reaching it with something material still in scope ends the task at `not mergeable, findings recorded`. Collision to watch for: not a **ceiling**, which bounds how large a change may grow, while a cap bounds how many times it may be revised. | A task whose third round still finds a material defect has reached a cap of two and is split rather than fixed again. |
| Issue split | `—` | The successor state of `not mergeable, findings recorded`: one successor issue carrying the branch's work as it stands, on a branch of its own cut from that commit, plus a child issue for each finding still open that the successor does not take. Where the successor takes every open finding, it alone is the split; an unapproved overrun is always among the findings it takes. Collision to watch for: not a parent-and-child decomposition under R11, which happens before work starts; a split happens after a task has stopped. | A branch stopped at its cap is not abandoned — its successor starts from the same commit, with the findings as its Definition of Done. |
| Ceiling | `—` | **A thing this kit does not have.** An approval is one number, named once, and it is the figure at landing; it reaches that figure and no further. Three review rounds each wrote a way for an approval to reach past its number — optional, bounding the measured outturn, covering findings-driven growth — and a later round falsified each, so the reach does not exist. Collision to watch for: not the **cycle cap**, which bounds how many times a change may be revised, where a ceiling would have bounded how large it may grow. | Growth past the approved figure is absorbed, routed to a child issue where the finding is non-material, or ends at the cap in a split. There is no second approval. |
| Review record | `—` | What one review round writes on the issue so a later reader can check it, under the heading `## Review record — round N`: the commit reviewed, the reviewer, the lens, what it was briefed on, what it was barred from, the independence claimed, the cycle, the raw findings, the fixes, and the verdict — ten fields, fixed by [What a round records](engineering-discipline.md#what-a-round-records). The reviewer writes nine; `Fixes` is the author's, added as a reply under the round it answers, because the fixes land after the round ends. A verdict that does not name what it read is not evidence, and the verdict itself comes from a closed vocabulary. | "LGTM" is not a review record. Neither is "reviewed `c98f807` under the adversarial lens, three findings, all fixed": it names no cycle, no brief and no bar, so a later reader cannot check what the reviewer could see. |
| Resource record | `—` | The model, effort, tokens and elapsed time a task spent, per gate **part** and in total, written as a section (after `## Verdict`) of its [`tasks/<id>.md`](tasks/) file at close-out and required by gate step 8 ([ADR-0007](adr/0007-record-task-resource-use.md), which decides it against the [routing](engineering-discipline.md#model-tiers) it evidences). **Recorded, not budgeted** — it carries no approval number and no cap, and an overrun of tokens or time is not a finding. Collision to watch for: not the **review record**, which is what a review round writes on the *issue*; a resource record is what a task writes in its own *file* about what running it cost. | A row whose expected tier is *reasoning* but whose model is an execution-tier one is a mismatch a reader raises; `not reported` fills a cell the harness cannot, and a human part's model columns read `not applicable`. |
| Heading anchor | `—` | The fragment a link uses to jump to one heading — the part after `#`. A forge derives it from the heading text by a fixed **slug** rule: lowercase, drop punctuation, and replace **each** space with a hyphen. Collision to watch for: the rule does not collapse runs, so `## R5 — Deterministic over LLM-based` yields `r5--deterministic-over-llm-based` with **two** hyphens, because removing the em-dash leaves two spaces. [`link-lint.sh`](links/link-lint.sh) checks these. | A checker that collapses whitespace reports 25 false failures on this repository's own rule anchors. |
| Material | `—` | Of a finding: one that changes an exit code, an assertion, a behaviour on an adopter's tree, a claim in the tree, or a Definition-of-Done item; wording, style and layout are not. A claim in the tree counts only when a reader could act on it and the change makes it false or leaves it false. Defined in the [review rounds](engineering-discipline.md#reviewing-until-findings-decay), which stop on `nothing material in scope`. Collision to watch for: not the everyday "important" — a finding can matter to a reader and still be wording. | A `must` softened to `should` in a rule is material; a comma moved in the same sentence is not. |
| Frozen head | `—` | The named commit a review round reads. Nothing lands on the branch after it except a fix to a finding of that round, a plain merge of the default branch, which re-freezes the head and consumes no cycle, or the close-out bookkeeping that gate step 8 requires of the landing pull request; the first two produce a frozen head a next round names, the close-out is named by none, and the last round's verdict is on it. A branch carrying such a verdict is never rebased, because a rebase rewrites the SHA the verdict names. Collision to watch for: not version control's `HEAD`, which moves with every commit — a frozen head is one SHA written into the review record, and it stays that SHA after the branch moves on. | Round 2 reviewed `c9af4e4`; its fixes landed as `b569583`, which round 3 named as its frozen head and found nothing material in. |
| Revealed defect | `—` | A defect a review round finds that is pre-existing and off the path the Definition of Done names. It leaves the branch as a new issue, opened by the author with its measurement before the merge — a blocker if it is a silent false green, normal if it fails loudly. Its counterpart is a defect *in the change*, fixed inside the budget. Collision to watch for: "revealed" says where the defect sits, not who found it — a defect the branch itself introduced is in the change however it came to light. | A linter that misreads a spaced path, found while reviewing a change to a different check, opens its own issue instead of entering the branch. |

## 1. Counting text

The terms of what `tally` counts. They follow rules 1 to 3 of the
[problem statement](facts/problem-statement-brief.md) and the answers in
[`F-0001`](facts/F-0001-setup-answers.md).

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Line | `—` | A run of characters that ends with a line feed. The last line of a file counts when the file does not end with a line feed, and an empty file has zero lines. Collision to watch for: the classic `wc -l` counts line feeds only, so it gives one line less than `tally` for a file without a final line feed. | `"one\ntwo"` is two lines; `"one\ntwo\n"` is also two lines; an empty file is zero lines. |
| Line feed | `LF` | The control character U+000A that ends a line. It is the only character that ends a line in `tally`. | A file written on Linux ends each line with one LF. |
| Carriage return | `CR` | The control character U+000D. In `tally` it ends no line: a CR before a line feed is part of the line and counts as one character, like any other code point. | The text `"a\r\n"` is one line, one word and three characters. |
| Carriage return and line feed | `CRLF` | The pair CR then LF, which ends a line in text written on Windows. `tally` counts it as two characters and one line end. | A file of two lines in CRLF, `"a\r\nb\r\n"`, gives 2 lines, 2 words and 6 characters. |
| Word | `—` | A run of characters that are not white space, where white space is a character of the Unicode property `White_Space`. Collision to watch for: not the ASCII white space of many tools — a no-break space (U+00A0) or an ideographic space (U+3000) also separates two words. | `"a b"` is two words, because U+00A0 has the property `White_Space`. |
| `White_Space` | `—` | The Unicode character property that lists the white-space characters, among them the space, the tab, LF, CR, the no-break space and the ideographic space. In Go, `unicode.IsSpace` follows the same set for the code points of the property. | A word ends at any of these characters, not only at a space. |
| Character | `—` | One Unicode code point of a text in UTF-8. Collision to watch for: not a byte, and not a user-perceived character — `é` written as one code point is one character and two bytes, and `é` written as `e` plus a combining accent is two characters. | `"héllo"` is five characters and six bytes. |
| Code point | `—` | One number of the Unicode character set, from U+0000 to U+10FFFF, which UTF-8 encodes in one to four bytes. Collision to watch for: Go calls a code point a `rune`. | The euro sign is the code point U+20AC, three bytes in UTF-8. |
| Unicode Transformation Format, 8-bit | `UTF-8` | The encoding of Unicode text in one to four bytes for each code point. A file that is not valid UTF-8 is not text for `tally`: it gets a message on standard error, no row, no share of the total, and the exit code 1. | The byte `0xFF` alone is never valid UTF-8, so a file that holds it is reported and skipped. |
| American Standard Code for Information Interchange | `ASCII` | The 128 code points U+0000 to U+007F, each one byte in UTF-8. The time target of `tally` is measured on a file of ASCII text. | A file of ASCII text has as many characters as bytes. |
| Kibibyte | `KiB` | 1,024 bytes. `tally` reads each file in fixed buffers of 64 KiB. | A buffer of 64 KiB holds 65,536 bytes. |
| Mebibyte | `MiB` | A mebibyte, 1,048,576 bytes. The time target is for a file of 10 MiB, and the memory target is 64 MiB of heap. | A file of 10 MiB holds 10,485,760 bytes. |
| Gibibyte | `GiB` | A gibibyte, 1,073,741,824 bytes. The memory target is for a file of 1 GiB. | A file of 1 GiB is 16,384 buffers of 64 KiB. |
| Buffer boundary | `—` | The place where one buffer of 64 KiB ends and the next begins. A UTF-8 sequence, and the detection of invalid UTF-8, must be handled across it, because a code point of two to four bytes can be cut there. | A three-byte euro sign whose first byte is the last byte of a buffer is still one character. |

## 2. The command and its output

The terms of how `tally` is run and what it prints. They follow rules 4 to 7 of
the problem statement and the answers in [`F-0001`](facts/F-0001-setup-answers.md).

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Flag | `—` | An option of the command: `-l` selects the line count, `-w` the word count, `-c` the character count. Flags may be combined; with no flag, all three counts are printed. Collision to watch for: `-c` is the byte count in the classic `wc`, but the character count in `tally`. | `tally -l -c notes.txt` prints the lines and the characters of `notes.txt`. |
| Fixed order | `—` | The order of the counts in a row: lines, then words, then characters, whatever the order of the flags on the command line. | `tally -c -l a.txt` prints the lines before the characters. |
| Row | `—` | One line of the output: the counts that the flags select, then the file name, each separated from the next by one space. The row for standard input has no name. | `3 12 70 notes.txt` |
| `total` row | `—` | The last row when two or more files are named: the sums of the counts of the files counted without an error, then the word `total`, in the layout of the other rows. A file that cannot be read, or is not valid UTF-8, adds nothing to it. | `5 20 110 total` |
| Standard input | `stdin` | The stream that `tally` reads when no file name is given. The name `-` does not mean standard input: it is a file named `-`. | `cat notes.txt \| tally` prints one row with no name. |
| Standard output | `stdout` | The stream that receives the rows. | `tally a.txt > counts.txt` writes the rows to a file. |
| Standard error | `stderr` | The stream that receives the messages of a file that cannot be read or is not valid UTF-8, with the file name and, for an unreadable file, the reason. | `tally missing.txt 2> errors.txt` writes the message to a file. |
| Exit code | `—` | The number `tally` returns to the shell: 0 when no error occurs, 1 when at least one file could not be read or was not valid UTF-8. The other files are still counted before the exit. | `tally a.txt missing.txt; echo $?` prints the row of `a.txt`, then `1`. |
| Unreadable file | `—` | A named file that `tally` cannot open or read — a missing file, a file without read permission, or a directory. It gets a message on standard error, no row, and the exit code 1. Collision to watch for: a directory is not skipped silently; it is an unreadable file. | `tally docs` reports that `docs` is a directory. |

## 3. The code and its quality targets

The terms of how `tally` is built and measured.

| Term | Abbr. | Description | Example |
|------|-------|-------------|---------|
| Go | `—` | The programming language and toolchain of `tally`. The product uses the Go standard library only, so `go.mod` holds no `require` line. | `go build` builds the `tally` binary. |
| Go module | `—` | The unit that Go builds and versions, described by `go.mod`. `tally` is one module with two packages. | The module holds the package `count` and the package `main`. |
| Package `count` | `—` | The Go package of `tally` that holds the functions that count the lines, the words and the characters of a reader, separate from the package `main` of the command. The idea owner defined this boundary (answer `Q-011`). | The unit tests of `tally` are the tests of this package. |
| Package `main` | `—` | The Go package of the command: it reads the flags, opens the files, prints the rows and sets the exit code. | The integration tests of `tally` drive this package against real files. |
| Statement coverage | `—` | The share of the statements of a package that the tests run, as `go test -cover` reports it. The target of `tally` is at least 90 percent for the package `count`. | `coverage: 93.1% of statements` meets the target. |
| Heap | `—` | The memory that the Go runtime allocates for values whose size or life is not known at compile time. The memory target of `tally` is a limit on the heap, not on the whole memory of the process. | `runtime.ReadMemStats` reports the heap in use as `HeapAlloc`. |
| Peak heap | `—` | The largest heap in use during a run, measured by sampling `HeapAlloc` every 10 milliseconds during the count. | Central processing unit | `CPU` | The processor of a computer. The time target is for a computer with 4 cores. | A laptop with 4 cores is a reference machine. |
| Solid-state disk | `SSD` | A storage device without moving parts. The reference machine of the time target has one, with the file already in the cache of the operating system. | The time test reads the file once before it measures, so the file is in the cache. |
| United States dollar | `USD` | The currency in which the idea owner set the money band of the delivery: below 50.00 USD the delivery goes on without asking, and 100.00 USD is the upper edge. | The answers `Q-012` and `Q-013` of `F-0001`. |
